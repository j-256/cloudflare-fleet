Deployment

Stand up a protected Worker without losing local mode

Hosted Fleet uses a custom-domain Worker, Cloudflare Access, D1, and encrypted Worker secrets. Generated deployment and operator files stay ignored; the committed defaults are safe, read-only, and unscheduled.

Prerequisites

  • Node.js 22 or newer and npm
  • A Cloudflare account with an active zone for the Fleet hostname
  • Permission to create Workers, a D1 database, a custom domain, and a Cloudflare Access application
  • An account API token scoped to the resources Fleet should inspect and, if enabled, change
  • A configured Cloudflare Zero Trust team domain and identity provider
Begin read-only

The configuration generator defaults to FLEET_READ_ONLY=true. Inspect the deployed inventory and Access boundary before regenerating with --write.

Hosted path

Provision the Worker

1

Install the pinned toolchain

The lockfile pins Wrangler, the Access JWT library, and the browser test stack.

npm ci
2

Create the D1 database

Record the database identifier returned by Wrangler. The generated configuration binds it as FLEET_DB.

npx wrangler d1 create cloudflare-fleet
export CLOUDFLARE_FLEET_D1_DATABASE_ID="the-returned-database-id"
3

Create the Access application

In Cloudflare Zero Trust, create a self-hosted application for the exact Fleet hostname and attach an Allow policy for the intended operators. Copy the Application Audience tag from the application settings and use the full HTTPS team domain as the issuer. The Worker validates both values on every non-loopback request.

Cloudflare documents the flow in Publish a self-hosted application and explains the audience and issuer in Validate JWTs.

4

Generate the ignored Wrangler configuration

Use an exact custom-domain hostname with no existing CNAME. Cloudflare creates the DNS record and certificate when Wrangler deploys the custom domain.

export CLOUDFLARE_ACCOUNT_ID="your-account-id"
export CLOUDFLARE_ACCESS_AUD="your-access-application-audience"
export CLOUDFLARE_ACCESS_TEAM_DOMAIN="https://your-team.cloudflareaccess.com"

npm run configure:hosted -- \
  --account-id "$CLOUDFLARE_ACCOUNT_ID" \
  --database-id "$CLOUDFLARE_FLEET_D1_DATABASE_ID" \
  --hostname fleet.example.com \
  --access-aud "$CLOUDFLARE_ACCESS_AUD" \
  --access-team-domain "$CLOUDFLARE_ACCESS_TEAM_DOMAIN"

The command writes mode-restricted wrangler.jsonc. That file contains account and deployment identifiers, so Git ignores it. wrangler.example.jsonc documents the portable shape without live values.

5

Apply storage and deploy the secret with the code

Wrangler accepts an ignored dotenv file through --secrets-file, allowing the first code version and encrypted secret to deploy together. Delete the local secret file after deployment if the shell environment is your preferred source of truth.

npm run db:migrate:remote
umask 077
printf 'CLOUDFLARE_API_TOKEN="%s"\n' "$CLOUDFLARE_API_TOKEN" > .dev.vars.production
npm run deploy -- --secrets-file .dev.vars.production

The custom domain is the Worker origin, so Cloudflare manages its DNS record and certificate. The Worker serves no workers.dev endpoint and disables preview URLs.

6

Verify Access and inventory

Open the configured hostname in a normal browser. Access should authenticate first, then Fleet should report a read-only session and begin loading the account. Test an unauthenticated private window as well: the Worker itself must reject a request that arrives without a valid Access assertion.

7

Opt into reviewed writes

After reviewing the account boundary, Access policy, proxy allowlist, and read-only inventory, regenerate the same ignored file with --write and deploy again.

npm run configure:hosted -- \
  --account-id "$CLOUDFLARE_ACCOUNT_ID" \
  --database-id "$CLOUDFLARE_FLEET_D1_DATABASE_ID" \
  --hostname fleet.example.com \
  --access-aud "$CLOUDFLARE_ACCESS_AUD" \
  --access-team-domain "$CLOUDFLARE_ACCESS_TEAM_DOMAIN" \
  --write

npm run deploy

Enable scheduled endpoint monitoring

Monitoring is a separate opt-in from reviewed writes. Regenerate the ignored Wrangler configuration with the ordinary identity arguments and --monitor. This sets FLEET_MONITOR_ENABLED=true and manages one * * * * * Cron Trigger. The dispatcher assigns each invocation exactly one lane; a five-minute cycle reserves one minute for analytics, one for catalog maintenance, and three for probe shards. Each invocation receives an independent Workers Free CPU budget, and the lanes do not run concurrently on the same scheduled minute. Monitoring does not change FLEET_READ_ONLY.

npm run configure:hosted -- \
  --account-id "$CLOUDFLARE_ACCOUNT_ID" \
  --database-id "$CLOUDFLARE_FLEET_D1_DATABASE_ID" \
  --hostname fleet.example.com \
  --access-aud "$CLOUDFLARE_ACCESS_AUD" \
  --access-team-domain "$CLOUDFLARE_ACCESS_TEAM_DOMAIN" \
  --hookrelay-service hookrelay \
  --monitor

npm run db:migrate:remote
npx wrangler secret put FLEET_MONITOR_HOOKRELAY_URL
npx wrangler secret put FLEET_MONITOR_HOOKRELAY_HMAC
npm run deploy

The URL must identify a Hookrelay cloudevents subscription and is secret because it contains the route slug. The HMAC must match that subscription's sender secret. Both values remain encrypted Worker secrets; the configuration file carries only their required binding names. The generated FLEET_MONITOR_HOOKRELAY service binding invokes the named Hookrelay Worker without an Internet round trip, while global_fetch_strictly_public keeps same-zone endpoint probes on Cloudflare's public path.

The detector reads account-wide edge analytics, refreshes exact proxied DNS names one zone per maintenance invocation, and probes a deterministic shard of the selected operational subset. It does not depend on Cloudflare Health Checks or Passive Origin Monitoring. Its hard budget stays below the Workers Free limit of 50 external subrequests per invocation, each probe shard contains at most 10 endpoints, and its connection pool stays at Cloudflare's six-connection limit. The account API token therefore needs the same zone and DNS reads as Fleet plus access to the HTTP analytics dataset.

After the first catalog completes, open the authenticated /api/monitor endpoint. A healthy durable state shows a completed catalog, an analytics watermark, selected endpoint counts, no unexpected open incidents, and no pending deliveries. Use Workers Observability for scheduled lane outcomes and CPU or wall-time measurements. The first catalog spans multiple maintenance invocations because each invocation refreshes at most one zone.

To stop monitoring, regenerate with --no-monitor and deploy. The generated empty Cron list removes the managed trigger. Existing incident history remains in D1, and disabling the trigger performs no deletion or remediation.

Operator policy exceptions

Fleet ships with no policy exceptions or endpoint overrides. If one zone intentionally uses an exact Email DNS record that differs from the derived fleet baseline, or monitoring should include or exclude an exact proxied hostname, copy fleet-policy.example.json to ignored fleet-policy.json and edit the relevant fields. Local launches load it directly; configure:hosted validates and embeds the same document into the ignored Wrangler variables.

cp fleet-policy.example.json fleet-policy.json
npm run configure:hosted -- ...

An Email DNS exception does not hide the matrix difference. It removes only the exact allowed variant from actionable policy drift. Endpoint exclusions prevent scheduled analytics observations and probes for exact cataloged names; an existing incident closes with a policy-excluded reason and no recovery event. Inclusions add exact proxied names even when successful traffic is below the automatic threshold. Exclusions and inclusions cannot overlap.

Import existing local intent and activity

When moving an established local fleet to hosted mode, apply the migration first and import the ignored account-scoped state file once.

npm run state:import:hosted -- state.json

The importer reads the D1 identifier from the ignored Wrangler configuration and refuses to replace populated hosted state. Use --force only after reviewing both local and remote data.

Keep the local interfaces

Hosted deployment does not replace local mode. On macOS, provide the account token and identifier in the shell and launch the ordinary browser workflow. It shares the same UI, policy, intent schema, write planner, activity model, and verification code.

export CLOUDFLARE_API_TOKEN="your-account-token"
export CLOUDFLARE_ACCOUNT_ID="your-account-id"
./launch.sh --read-only

Use ./launch.sh --write for the full local workflow. Local state defaults to ignored state.json; set CLOUDFLARE_FLEET_STATE_FILE to an absolute path for another profile.

The local fleet CLI and stdio MCP server inherit the same credentials and use the same ignored state profile. Start them from the project directory after installing dependencies:

npm run fleet -- alignment list --format json
npm run mcp

An MCP client can launch node /absolute/path/to/cloudflare-fleet/src/mcp.mjs directly. Keep the token in the inherited process environment, not a tracked or shared client configuration. The server opens no listener and exposes only named audit, alignment, and activity tools.

Publish these docs with GitHub Pages

The site is dependency-free and uses relative links, so it works beneath a project path. After the standalone repository exists, open repository Settings, choose Pages, select Deploy from a branch, choose the default branch and /docs, then save. GitHub documents this branch-source option in Configuring a publishing source.

Run npm run docs:serve to preview the same files at http://127.0.0.1:4173/. The publication check validates every local documentation link and rejects symbolic links so the branch-source Pages build remains compatible.

Create a clean standalone source tree

The private monorepo history can contain files that should never become part of a public repository. Export the project from its tracked publication state instead of carrying that history forward.

npm run check:publication
npm run export:standalone -- --output ../cloudflare-fleet-public

The exporter copies regular tracked files, refuses a non-empty destination, and excludes operator state and deployment configuration. It does not initialize a repository, create a remote, or push anything.
